# Windows CLI 异常退出根因

## 结论

Windows CLI 在收到成功 IPC 响应后以 `0xC0000409` 退出，根因是客户端把 `interprocess 2.4` 命名管道切换为 `PIPE_NOWAIT`，同时继续使用该库基于 `ReadFileEx` / `WriteFileEx` 的同步重叠 I/O 实现。成功请求过程中的暂时无数据状态会让底层操作提前返回错误，并进入库的不可展开保护路径，最终触发 Windows fast-fail。

这不是工作区创建、Git 初始化、CLI JSON 输出或进程 Job 引起的问题。服务端已经正确完成请求，异常只发生在客户端成功 IPC 路径。

## 稳定复现

使用 `scripts/复现WindowsCLI正常退出.ps1` 启动真实 Paneflow 桌面服务端，再由同一个二进制执行 CLI 子命令。脚本隔离用户配置和会话，通过第二条真实命名管道请求核对服务端状态，并检查客户端退出码、标准输出和标准错误。

修复前连续三次执行 `new --cwd <真实目录>` 的结果均为：

- 服务端工作区数量为 `1`；
- 客户端退出码为 `0xC0000409`；
- 标准输出和标准错误均为空；
- 客户端往返耗时分别约为 `386 ms`、`319 ms` 和 `275 ms`。

`ls` 在空服务端上同样异常退出。`status 不存在的终端` 已成功完成前置 `surface.list`，随后进入本地目标不存在分支，仍以相同代码异常退出。因此工作区创建和成功结果渲染都不是必要条件，成功完成一次 IPC 读写才是共同边界。

## 单变量排除

以下探针均只改变一个条件：

1. 跳过 CLI 的 Windows Job 绑定后症状不变，排除 `KILL_ON_JOB_CLOSE`。
2. 保留请求与响应，只取消 `ConnectOptions::nonblocking_stream(true)` 后，客户端退出码恢复为 `0`，完整 JSON 输出出现，服务端状态仍正确。
3. `--help`、子命令帮助、缺少 `--cwd` 和 IPC 不可达均按既有退出码正常结束，说明不经过成功 IPC 响应的路径不触发问题。

## 修复约束

正式修复必须同时满足：

- 不再把 `interprocess` 同步命名管道设置为 `PIPE_NOWAIT`；
- 保留单次请求响应的 10 秒读写截止时间；
- 超时后取消并回收未完成的 Windows 重叠 I/O，不能用遗留线程实现超时；
- 保持 256 KiB 响应上限、JSON-RPC 协议和 CLI 命令语义不变；
- 以真实 GUI 服务端与真实 CLI 进程作为最终回归边界。
