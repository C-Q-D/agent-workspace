# A013 后台资源生命周期审查

## 审查结论

本原子只审查，不改变运行时。AgentWorkspace 的终端输出、配置、主题、文件与 Diff 主路径大多基于事件；应用也已对 IPC、Telemetry、会话结果和 Diff 实体设置上限。当前没有发现“每个终端都扫描 Git/文件系统”的默认轮询。

但应用启动后仍存在 7 组应用级周期任务，其中 50 ms 自动化 channel drain、50 ms 文件事件 drain 和 200 ms Git 事件 drain 即使没有事件也会唤醒。它们不会随 N×N 窗口数倍增，却是 v1 低空闲 CPU 的主要架构债务。30 秒 Git fallback 会对每个唯一工作区执行最多 3 个有 10 秒 deadline 的 Git 子进程，并读取最多 200 个未跟踪文件；这是最明确的 N 工作区放大风险。

Windows v1 的终端进程守护是一个应用级 Job Object，不会为每个终端再启动轮询守护进程。每个真实终端仍必然拥有 ConPTY/Alacritty I/O 线程和一个事件消费任务，这部分随终端数线性增长。

## 应用启动即存在的资源

| 资源 | 类型/频率 | 启动条件 | 停止条件 | 所有者 | 倍增风险与结论 |
|---|---|---|---|---|---|
| 光标闪烁 | 单一 async timer，约 530 ms | 应用构造 | `WeakEntity` 更新失败 | 应用全局 `BlinkPhase` | 1 个，不随终端数增长；只通知观察者 |
| Config watcher | OS 非递归 watcher + 1 阻塞事件线程，300 ms debounce | 能解析配置目录 | 进程退出 | watcher 线程自身 | 事件驱动，不是轮询；成功 reload 只覆盖单一 pending slot |
| Theme watcher | OS 非递归 watcher + 1 事件线程，300 ms debounce | watcher 初始化成功 | 进程退出 | watcher 线程自身 | 事件驱动；失败时 `active_theme()` 在被调用时最多每 500 ms stat 一次 |
| Git watcher drain | async timer，200 ms | 应用构造 | 应用实体销毁 | `PaneFlowApp` | 1 个全局任务；空闲仍每秒唤醒 5 次 |
| Files watcher drain | async timer，50 ms | 应用构造 | 应用实体销毁 | `PaneFlowApp` | 文件栏关闭时 watcher/rx 为空但 timer 仍每秒唤醒 20 次 |
| Automation drain | async timer，50 ms | 应用构造 | 应用实体销毁 | `PaneFlowApp` | 1 个全局任务；统一轮询 IPC、surface generation、配置 slot、主题 flag、update slot |
| Git fallback | async timer，30 秒 | 应用构造 | 应用实体销毁 | `PaneFlowApp` | 对工作区与遗留 Agents 项目的唯一 cwd 逐个探测，随目录数线性增长 |
| stale PID sweep | async timer，30 秒 | 应用构造 | 应用实体销毁 | `PaneFlowApp` | 遍历已注册 Agent session；公开产品面退出后仍存在遗留成本 |
| active port rescan | async timer，5 秒 | 应用构造 | 应用实体销毁 | `PaneFlowApp` | 只为已有 active port 且无 pending scan 的工作区调度；随活跃服务工作区增长 |
| update check | 1 个 detached OS 线程，单次请求 deadline 30 秒 | 每次启动 | 请求完成或超时 | 返回的共享状态 slot | 每启动一次，不重复定时检查 |
| telemetry flusher | async timer，5 秒 | 每次创建 telemetry handle | handle `is_active` 为 false | 活动 `TelemetryClient` Arc | Null/禁用句柄首个 tick 后退出；配置切换会使旧句柄 deactivate |
| IPC server | 1 accept 线程 + 每连接 handler 线程 | 应用构造 | 监听失败或进程退出 | IPC server | Windows blocking accept；连接总数上限 32，GPUI 请求队列 256、每 tick 处理 64 |

Config/Theme watcher 的注释声称 watcher drop 会关闭 channel，但实际 watcher 被移动到事件线程，线程同时持有 receiver；应用没有保存 stop handle。正常产品只有一个应用实例，故它们是“进程寿命资源”，不是每次打开设置重新创建的泄漏。文档和真实停止条件应在后续生命周期收敛时统一。

## 随终端数量增长的资源

| 资源 | 每终端成本 | 空闲行为 | 结束方式 | 风险 |
|---|---|---|---|---|
| ConPTY/Alacritty EventLoop | 1 个 I/O 线程及 PTY/子进程句柄 | 阻塞等待 I/O | `TerminalState::drop` 发送 Shutdown，随后终止/回收子进程 | 必要的线性成本 |
| TerminalView 事件任务 | 1 个 async receiver | `events_rx.next().await` 阻塞，零轮询 | channel 关闭或 entity 销毁 | 必要的线性成本 |
| 终端事件 channel | futures unbounded channel | 有输出才入队；4 ms 内最多批 100 个事件 | producer/consumer 释放 | 持续输出快于 UI 消费时没有硬队列上限，是内存峰值风险 |
| pending input | 最多 64 KiB | 只在 PTY 尚未完成创建时使用 | promote 后 drain | 已有硬上限 |
| Windows 进程守护 | 不增加单独守护线程/进程 | 单一 Job Object 由内核持有 |应用退出时 Job handle 关闭 | 优于逐终端轮询 |

矩阵缩小时隐藏终端仍需持续执行 CLI，因此不能暂停 PTY I/O；现有隐藏重绘门控只减少 UI 唤醒，不应中断输出消费。

## 聚焦文件与 Review 生命周期

| 资源 | 启动条件 | 停止/释放 | 放大倍数 |
|---|---|---|---|
| Files watcher | 只在放大窗口文件栏 hydration 后，为 root 和展开目录注册非递归 watch | 缩小、进入 Diff、切换 root 或关闭文件栏时清空 watcher/rx | 只有一个聚焦文件上下文；展开目录数决定 OS watch 数 |
| Files hydration | 打开/重定向文件栏 | generation/root/open 检查使旧结果失效 | 一次性后台目录读取 |
| Diff watcher | 聚焦工作区进入 Review 且 Diff view bootstrapped | `suspend()` 增加 epoch 并清空 `_watchers` | 当前 Review 实体；缓存实体已 suspend |
| Diff revalidate | watcher 事件 debounce/cooldown 后 | 单次后台 fingerprint 结束 | 随可见 worktree column 数增长 |
| Diff view cache | 退出 Review 或切换仓库后保留 rows | 仓库关闭时 prune，超过 6 个实体时 evict | 上限 6，缓存实体无 watcher |

文件 watcher 是事件驱动；50 ms 的是应用级 channel drain，不是对磁盘做 20 次/秒扫描。Diff watcher通过 channel await 与 timer debounce 工作，也不是周期扫描。

## Session discovery、缓存和遗留产品面

- Docked session discovery 只在用户打开会话栏时，对启用的 CLI 适配器分别 `smol::unblock` 扫描；generation 防止旧结果覆盖新工作区。
- session cache 是进程级 LRU，最多 10 个 `(agent, cwd)`；每源侧栏最多保留 100 行，Diff attribution 每列最多 50 行。
- CLI 安装探测缓存只覆盖固定 `TerminalAgent::ALL`，TTL 2 秒；它不会随用户路径无限增长，但如果调用发生在频繁 render 路径，可能周期性遍历 PATH。
- Agents 公开入口已隐藏，但 `projects`、session discovery、stale PID sweep、Git fallback 的 Agents cwd 分支仍被默认编译和部分常驻路径引用。A027～A038 应据公开边界裁剪其默认成本。

## Git、子进程与超时

30 秒 fallback 对每个唯一 cwd 执行 `GitDiffStats::from_cwd`：

1. `git rev-parse --verify HEAD`；
2. `git diff --shortstat <base> --`；
3. `git ls-files --others --exclude-standard -z`。

每个子进程都有 10 秒 deadline、256 KiB stdout 上限、关闭交互提示；未跟踪路径最多检查 1000 个，只有前 200 个文件读取内容，每文件最多 512 KiB。这避免单个仓库无限挂起或读取，但多个慢仓库在同一个 blocking task 中串行执行，理论最坏时间随工作区数线性增加。该任务不阻塞 GPUI 主线程，却会长期占用 blocking worker。

工作区创建的 `git init`、worktree 操作、Diff 加载和端口扫描均是显式事件/用户动作触发并有 deadline，不属于默认持续轮询。

## Update、Telemetry 与网络

- Update 每次应用启动都会创建一次检查线程，默认请求 GitHub feed，global timeout 30 秒；不是周期检查。
- Telemetry 只有用户明确启用且没有 kill switch 时为 Active。队列上限 1000，10 条或最老 30 秒触发发送，HTTP timeout 5 秒，失败丢弃且不重试。
- Telemetry flusher 每 5 秒检查一次内存队列；禁用配置重建 client 时旧 handle 被 `deactivate()`，旧 flusher随后退出。
- 当前“本地优先/Telemetry 最终策略”仍属于 A039～A040 和人工门 A109～A110，本审查只记录现状，不替用户决定。

## Helper 与进程守护

- Windows 主进程启动前创建一个带 `KILL_ON_JOB_CLOSE` 的 Job Object，并把自身加入；ConPTY shell 和后代继承该 Job。这里没有 500 ms 的逐终端守护轮询。
- `paneflow-shim`、`paneflow-ai-hook` 和 `paneflow-mcp` 被构建/打包不等于常驻。它们由 CLI/hook/MCP 调用时短期启动；A011 已记录 17 个发行 helper。
- AI hook 发送失败使用有限 backoff 后退出；shim 等待它启动的真实工具/子 hook，不由桌面应用空闲常驻。
- IPC server 是主应用内线程，不是额外 helper 服务；Windows 使用阻塞 named-pipe accept。

## 风险优先级

| 优先级 | 风险 | 后续归属建议 |
|---|---|---|
| 高 | 30 秒 Git fallback 对所有 cwd 做多子进程和未跟踪文件读取，N 工作区线性放大 | A015～A026 所有权收敛时改为事件/脏标记驱动，保留低频按需兜底 |
| 中 | 文件事件 drain 和 automation drain 各自以 50 ms 常驻唤醒，即使无文件栏/无 IPC | A033～A038 默认载荷收敛时合并事件唤醒或自适应空闲节流 |
| 中 | 每终端事件 channel 无硬上限，持续高速输出可能积压 | 后续性能原子用真实输出压力验证；修复必须保证不丢关键终端状态 |
| 中 | Config/Theme watcher 无显式 stop handle，真实生命周期是进程级，与部分注释不符 | 状态/所有权重构时增加应用持有的生命周期对象或修正文档契约 |
| 低 | 200 ms Git watcher drain 常驻唤醒 | 可与统一事件通道合并，不是当前 N 倍增源 |
| 低 | 5 秒端口、30 秒 stale PID、5 秒 Telemetry timer | 均有条件过滤；旧 Agents 默认路径退出后重新测量 |
