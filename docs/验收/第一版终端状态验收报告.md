# 第一版终端状态验收报告

## 当前结论

截至 2026-07-18，Windows 第一版的基础终端状态识别和左侧状态展示已通过真实进程验收。测试使用真实 PowerShell、真实 ConPTY 退出事件和真实 Windows 启动失败，没有使用 mock 终端、伪造状态或人为延迟。

## 验收环境

- 二进制：启用 `terminal-perf-metrics` 的 Release 构建。
- 被测提交：`f4356faab4ad1de950411a034f540642747f2085`。
- 二进制 SHA-256：`FFA8EC367125F013949A034DBEB386588665FF48B1DED1CFC44738BD3E485D81`。
- 工作目录：本地真实 Git 仓库 `agent-workspace/app`。
- 用户状态：脚本暂存并在 `finally` 中恢复真实 `paneflow.json` 和 `session.json`，实验状态不污染日常会话。

## 状态验收结果

1. 通过生产 `workspace.create` IPC 入口连续创建真实终端，创建响应在 PTY 后台 promote 前捕获到同源 `starting` 状态，不依赖高频轮询。
2. 正常运行的 PowerShell 在左侧显示为 `Running`。
3. 向真实 PTY 输入 `exit 0` 后，窗格保留并显示为 `Exited`，底层状态为 `normal_exited`。
4. 向真实 PTY 输入 `exit 7` 后，窗格保留并显示为 `Crashed`，底层状态为 `abnormal_exited`。
5. 将默认 Shell 临时切换为真实存在但不可执行的文本文件后，Windows `CreateProcess` 返回真实启动失败，窗格显示为 `Launch failed`，底层状态为 `launch_failed`。
6. 正常退出和异常退出后的 Surface ID 均保持不变，证明应用没有为隐藏退出状态而自动重建终端。
7. 验收结束后，所跟踪的 Paneflow 与 PowerShell 进程残留数量为 0。

## 事件与性能边界

- 状态变化由 PTY 创建结果和子进程退出事件驱动，没有为每个终端新增定时轮询。
- 工作区聚合状态使用固定优先级：启动失败、异常退出、启动中、运行中、正常退出；多窗格工作区只需在真实生命周期变化时重新聚合。
- `starting` 通常只存在数毫秒，因此验收读取生产创建响应中的同步状态快照；这不是测试专用状态，也没有延长终端启动时间。

## 结论边界

- 本次只验收基础终端生命周期，不推断 Codex CLI 或 Claude Code CLI 的任务语义，例如“等待用户输入”或“模型思考中”。
- 正常退出和异常退出的终端会保留，便于用户查看退出码和进行审查；用户主动关闭后才进入既有的窗格移除流程。
- 终端状态文字与颜色同时呈现，颜色不是唯一的信息载体。
