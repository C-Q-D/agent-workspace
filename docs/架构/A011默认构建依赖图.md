# A011 默认构建依赖图

## 结论

Windows 默认 `cargo build -p paneflow-app --target x86_64-pc-windows-msvc` 并不只生成一个
纯桌面 EXE。当前结构同时存在三种依赖关系：

1. `paneflow-app` 以 Rust 普通依赖直接链接 6 个内部 crate；
2. `src-app/build.rs` 无条件执行嵌套 Cargo，构建 3 个独立二进制并把字节嵌入主 EXE；
3. Windows Release 工作流又把 shim 复制成 16 个 Agent 命令别名，并连同 AI hook
   作为 17 个外部 helper 放入 MSI 和便携 ZIP。

因此，“不在 `cargo tree` 的主 EXE Rust 依赖图中”不代表“不进入主 EXE或发行包”。
`paneflow-shim`、`paneflow-ai-hook` 和 `paneflow-mcp` 虽不被 Rust 链接，却通过
`rust-embed` 进入主 EXE；shim 与 hook 还会作为独立文件重复进入 Windows 发行载荷。

可重复生成结构化事实：

```powershell
pwsh -NoProfile -File scripts/生成默认构建依赖图.ps1 `
  -Target x86_64-pc-windows-msvc `
  -OutputPath target/a011-default-build-graph.json
```

## 1. 默认构建入口

- Cargo workspace 有 10 个成员，`default-members = ["src-app"]`，所以裸
  `cargo build/run/test` 选择桌面包，见 `Cargo.toml:1`～`:19`。
- 桌面 Cargo 包仍名为 `paneflow-app`，公开二进制名是 `agent-workspace`，
  见 `src-app/Cargo.toml:1`～`:22`。
- 桌面包只声明 `terminal-perf-metrics`，没有 `default` feature；默认构建不会启用性能
  计数字段，见 `src-app/Cargo.toml:15`～`:18`。
- 桌面包存在 `src-app/build.rs` custom build target。该脚本不是可选 feature，所有正常
  debug/release 构建都会执行。

## 2. 默认 Windows 构建数据流

```text
cargo build -p paneflow-app --target x86_64-pc-windows-msvc
│
├─ Rust 普通依赖，链接进 agent-workspace.exe
│  ├─ paneflow-acp
│  ├─ paneflow-config
│  ├─ paneflow-ipc-client
│  ├─ paneflow-mcp-install
│  ├─ paneflow-process
│  └─ paneflow-telemetry
│
├─ src-app/build.rs 嵌套 cargo build --profile release-min
│  ├─ paneflow-shim.exe ─────┐
│  ├─ paneflow-ai-hook.exe ──┼─> src-app/target/embed/bin/<target>/
│  └─ paneflow-mcp.exe ──────┘          │
│                                       └─ rust-embed -> agent-workspace.exe
│
└─ src-app 自身模块
   ├─ ipc.rs：本地 IPC 服务端
   ├─ telemetry.rs + paneflow-telemetry：遥测运行时
   └─ update/*：更新检查和 MSI/便携安装逻辑

Windows Release 准备
│
├─ paneflow-shim.exe 复制为 16 个 Agent 命令别名
├─ paneflow-ai-hook.exe 作为第 17 个 helper
├─ WiX HelperBinaries -> MSI 的 bin/
└─ 生成Windows便携包.ps1 -> ZIP 的 bin/
```

`PANEFLOW_SKIP_EMBED_BUILD=1` 只能跳过嵌套编译，调用者仍必须预先填好 embed 目录，随后
还会执行总大小门禁；它不是“禁用嵌入”的产品 feature，见 `src-app/build.rs:24`、
`:128`～`:140`。

## 3. 主 EXE 的内部 Rust 依赖

`cargo tree -p paneflow-app --target x86_64-pc-windows-msvc --depth 1 -e normal,build`
证明下列 6 个内部 crate 是桌面包的普通直接依赖：

| crate | 主 EXE 关系 | 当前用途 | 证据 |
|---|---|---|---|
| `paneflow-acp` | 直接链接 | 遗留 Agent 身份与 `CLAUDECODE` 环境清理 | `src-app/Cargo.toml:79`～`:81` |
| `paneflow-config` | 直接链接 | 配置、Schema、数据布局与 watcher | `src-app/Cargo.toml:78` |
| `paneflow-ipc-client` | 直接链接 | 同一 EXE 的脚本化 CLI 在 GUI 前连接运行实例 | `src-app/Cargo.toml:95`～`:98` |
| `paneflow-mcp-install` | 直接链接 | MCP/hook 安装、状态和设置页 | `src-app/Cargo.toml:86`～`:90` |
| `paneflow-process` | 直接链接 | Git、更新、MCP 等外部进程的超时与输出上限 | `src-app/Cargo.toml:91`～`:94` |
| `paneflow-telemetry` | 直接链接 | PostHog 客户端、匿名 ID 与事件队列 | `src-app/Cargo.toml:82`～`:85` |

`src-app` 只有 `winresource` build dependency；GPUI、Alacritty、Zed markdown/theme/ui、
文件 watcher、通知、HTTP、压缩、Diff 和 tree-sitter 等第三方依赖也直接进入默认图，但
本原子重点记录影响 v1 产品边界的内部依赖。

## 4. 重点组件逐项结论

| 组件 | Rust 链接到主 EXE | 构建时生成 | 字节嵌入主 EXE | Windows 外部载荷 | 运行时路径 |
|---|---:|---:|---:|---:|---|
| `paneflow-ai-hook` | 否 | 是 | 是 | 是，`bin/paneflow-ai-hook.exe` | 可提取到数据根 `bin/` 或版本缓存 |
| `paneflow-mcp` | 否 | 是 | 是 | 否 | GUI 启动或 `mcp install` 时提取到稳定数据根 |
| `paneflow-mcp-install` | 是 | 随主 EXE 编译 | 不适用 | 无独立 EXE | 主进程内执行配置读写和安装命令 |
| `paneflow-shim` | 否 | 是 | 是 | 是，以 16 个 Agent 名复制 | 终端 PATH 前置目录或安装包 `bin/` |
| IPC client | 是 | 随主 EXE 编译 | 不适用 | 也被 hook/MCP 独立链接 | 脚本化 CLI、hook、MCP 请求 |
| IPC server | 是，`src-app/src/ipc.rs` | 随主 EXE编译 | 不适用 | 无独立文件 | GUI 启动后命名管道监听 |
| Telemetry | 是 | 随主 EXE 编译 | 不适用 | 无独立文件 | bootstrap 创建 flusher；策略待 A109 |
| Updater | 是，源码模块 | 随主 EXE 编译 | 不适用 | 无独立 updater EXE | GUI 检查、`--update-and-exit`、MSI relay |

### 4.1 AI hook

`paneflow-ai-hook` 是独立 bin，只依赖 `paneflow-ipc-client`、Serde 和 JSON，
见 `crates/paneflow-ai-hook/Cargo.toml`。它不出现在 `paneflow-app` 的 Rust 逆向依赖树，
但 build script 在 `src-app/build.rs:169`～`:173` 构建并嵌入，Release 又在
`.github/workflows/release.yml:444` 把它复制到外部 helper 目录。

### 4.2 MCP bridge 与安装引擎

`paneflow-mcp` 是小型独立 bin，依赖 IPC client；它被嵌入但不作为 MSI/ZIP helper 文件，
运行时由 `src-app/src/ai_hooks/extract.rs:185` 之后的稳定提取路径写入用户数据根。
`paneflow-mcp-install` 则是普通库依赖，直接扩大主 EXE 链接图，并由命令行与设置页调用。

### 4.3 Shim 与 16 个命令别名

`paneflow-shim` 自身只生成一个二进制。Windows Release 在
`.github/workflows/release.yml:423`～`:443` 将同一文件复制为：

`claude`、`codex`、`opencode`、`pi`、`hermes`、`grok`、`amp`、`cursor-agent`、
`gemini`、`kiro-cli`、`agy`、`copilot`、`codebuddy`、`droid`、`qodercli`、
`openclaw`。

WiX 和便携脚本都把这些 16 个别名加 AI hook 作为 17 个外部 helper。`paneflow-shim.exe`
原名和 `paneflow-mcp.exe` 不进入当前 Windows 包的 `bin/`。

### 4.4 IPC

仓库没有名为 `paneflow-ipc` 的独立 crate。客户端是
`paneflow-ipc-client`；服务端实现位于桌面包 `src-app/src/ipc.rs`，由
`src-app/src/main.rs:37` 无条件登记。桌面 EXE、AI hook 和 MCP bridge 分别链接客户端，
因此 IPC 是主 EXE与两个嵌入二进制之间的共享运行时边界。

### 4.5 Telemetry

`paneflow-telemetry` 是主 EXE 普通直接依赖，并引入 `ureq`、UUID、Serde 和 JSON。
`src-app/build.rs:53`～`:58` 还监听 `POSTHOG_API_KEY` 与 `POSTHOG_HOST`，Release workflow
把编译期密钥传给唯一 Release build。bootstrap 无条件建立 telemetry flusher 调用路径，
但发送是否生效还受配置和密钥控制。A011 只确认它进入默认构建，不替 A109 决定去留。

### 4.6 Updater

Updater 不是独立 workspace crate，而是 `src-app/src/update/` 源码模块，
`src-app/src/main.rs:62` 无条件登记。主依赖图中的 `ureq`、`minisign-verify`、`sha2`、
`flate2`、`tar` 等支持检查、校验和平台安装；Windows 还提供 MSI relay。A033～A042
需要决定默认发行是否保留更新路径及其载荷。

## 5. build script 与发行包不是同一层

当前有两份 helper 供应路径：

- **嵌入路径**：每次正常桌面构建由 `src-app/build.rs` 自行构建三项 release-min
  二进制，`assets::Bins` 把它们的字节写入主 EXE；运行时再提取。
- **签名发行路径**：Windows Release workflow 预构建并签名相同三项，填入 embed staging，
  同时准备外部 `paneflow-helpers`；主构建通过 `PANEFLOW_SKIP_EMBED_BUILD=1` 消费已签名字节。

MSI 与 ZIP 只读取 `paneflow-helpers`，不从主 EXE反向提取。若 A033～A038 精简 helper，
必须同时处理 build script 嵌入清单、运行时提取、Release workflow、WiX、便携脚本和载荷
一致性检查，不能只删除某个 Cargo member。

## 6. 仅开发或非默认构建

- `terminal-perf-metrics` 只有显式启用才编译性能计数字段。
- 各 crate 的 `[dev-dependencies]` 只服务测试，不进入正常主 EXE。
- `.github/workflows/run_tests.yml` 的 `cargo build --workspace --release` 会额外显式构建全部
  workspace 成员；它比本地默认成员范围更宽，不能据此推断桌面直接链接所有 crate。
- macOS/Linux 打包元数据仍在 `src-app/Cargo.toml` 和工作流中，但不属于 Windows v1
  默认目标；A032/A091 将处理公开路径与 CI 范围。

## 7. A014 前的事实建议

- `paneflow-config`、`paneflow-process` 和 IPC 边界属于 v1 核心保留候选。
- `paneflow-mcp-install`、MCP bridge、AI hook、shim、ACP 遗留身份和 Telemetry 都已经
  进入默认构建或默认发行，不能仅隐藏设置入口；需要明确“默认不编译/不打包”或保留理由。
- Updater 与 Windows MSI/ZIP 生命周期耦合，应作为发行能力单独决策，不与 Agent 编排代码
  一起粗暴删除。
- `src-app/build.rs` 的嵌套 Cargo 当前没有传 `--locked`；外层 `--locked` 不自动约束子
  Cargo。这是可复现构建风险，交给 A014/A098 记录责任原子，本原子不改构建行为。

## 8. 验证与限制

本报告使用：

```powershell
cargo metadata --format-version 1 --no-deps --locked
cargo tree -p paneflow-app --target x86_64-pc-windows-msvc --depth 1 `
  -e normal,build --prefix none --locked
pwsh -NoProfile -File scripts/生成默认构建依赖图.ps1
cargo build -p paneflow-app --release --locked
cargo test -p paneflow-app ai_hooks::extract::tests --quiet --locked
```

本次 Windows 复核结果：依赖图 7 个重点包、3 个嵌入二进制、17 个外部 helper 均匹配；
默认 Release 构建通过；嵌入与提取测试 12/12 通过。

限制：

- `cargo tree` 证明 Cargo 依赖闭包，不证明链接器最终保留每个函数；本文对“主 EXE模块”的
  表述以 Rust 编译单元和实际用户入口为界。
- 未对二进制做符号或 PE section 逆向；嵌入关系由 build script、`rust-embed` 源码和已有
  运行时提取测试证明。
- 不在 A011 变更 feature、Cargo member、打包清单或运行时提取行为。
